# WebgameSystem

`WindowHyun/liar`의 웹 버전을 Render의 상시 Node.js Web Service로 실행하는 프로젝트입니다.

## 로컬 실행

```bash
npm ci
npm run web
```

브라우저에서 `http://localhost:4100`을 엽니다.

## 테스트

| 명령 | 도는 것 | 언제 |
|---|---|---|
| `npm test` | 핵심: 서버·게임 규칙(브라우저 없이, 몇 분) | 고칠 때마다 |
| `npm run test:ui` | 화면: 브라우저로 띄우는 테스트(모바일 포함, 6분 안팎) | 화면을 고쳤을 때 |
| `npm run test:all` | 핵심 + 화면 + 오래 걸리는 백그라운드 복귀 테스트(20분 안팎) | 배포 전 |

- `test/` 안의 `*-test.js`는 자동으로 잡힙니다. 브라우저(playwright)를 쓰면 화면 테스트, 아니면 핵심 테스트입니다.
- 이름 일부를 붙이면 그 스위트만 돕니다. 예: `node test/run-all.js cover mind`
- 기본은 스위트마다 한 줄 요약이고, 실패한 것만 자세히 보여 줍니다. 전체 출력은 `--verbose`로 봅니다.
- 화면 테스트는 Playwright의 Chromium이 필요합니다(`npx playwright install chromium`).
- 연결이 끊겼다 다시 붙는 순서(옛 소켓이 늦게 닫힘, 확인 중 끊김 등)는 가짜 소켓·가짜 시계로 봅니다: 카드 게임은 `socket-race`(핵심), 라이어는 `liar-socket-race`(화면). 실제 네트워크로 폰을 내려놨다 돌아오는 경우는 `background-return`이 보고, 자리를 잃거나 15초 안에 다시 붙지 못하면 실패합니다.
- 셸에 잡힌 `PORT`는 스위트에 넘기지 않습니다. 시간이 넘거나 Ctrl+C를 누르면 스위트가 띄운 서버까지 함께 끕니다.

## 갈팡질팡 (여럿이 함께 하는 추리 게임)

포털의 "갈팡질팡" 채널로 들어갑니다. 후보 16개 중 숨겨진 정답 1개를 5라운드 안에 찾는 게임입니다.
라운드마다 비교할 수 있는 두 개념(A·B)이 나오고, 정답에 더 가까운 쪽을 알려 줍니다. 후보를 눌러 고른 뒤
제거하거나 정답으로 제출하고, 다음 라운드로 넘어가면 더 구체적인 힌트가 나옵니다. 끝나면 정답과 힌트 해설이 나옵니다.

- **여럿이 한 판을 같이 합니다.** 방 하나에 판 하나라서 모두 같은 후보·힌트를 봅니다. 왼쪽 참가자 목록에
  들어온 사람이 보이고, 다른 카드 게임처럼 각자 **준비**를 누른 뒤 누구든 **게임 시작**을 누르면 준비한 사람이
  참가자가 됩니다(최대 8명). 준비 안 한 사람과 중간에 들어온 사람은 구경하고 다음 판부터 참여합니다. 혼자
  접속해 있으면 준비 없이 바로 시작합니다.
- **판을 바꾸는 조작은 접속자 과반수의 동의가 필요합니다.** 후보 제거·정답 제출·다음 라운드·포기를 누르면 제안이
  되고(제안한 사람은 찬성으로 칩니다), 접속 중인 참가자의 과반수(절반을 넘는 수)가 찬성하면 실행됩니다. 반대가
  많아 과반수가 될 수 없으면 바로 취소되고, 30초 안에 결판이 나지 않아도 취소됩니다. 끊긴 사람은 투표 인원에서
  빠지고, 접속한 참가자가 한 명뿐이면 바로 실행됩니다. 어떤 조작에 동의를 받을지는 `web/galpang-room.js`의
  `NEEDS_CONSENT` 표 하나로 정합니다.
- **정답 제출은 한 번뿐입니다.** 맞히면 이기고, 틀리면 그 자리에서 게임이 끝나며 정답이 공개됩니다(5라운드가
  다 지나도 집니다). 제거한 후보나 범위 밖 번호를 제출하는 것은 제출로 치지 않아서 잘못 눌러도 게임이 끝나지
  않고, 화면에서는 제출 전에 한 번 더 확인합니다.
- **정답 후보를 지워도 그 자리에서 끝나고 정답이 공개됩니다.** 그래서 후보를 지우는 것은 "이 후보는 정답이
  아니다"라는 내기입니다. 지웠는데 게임이 이어지면 그 후보는 정답이 아니었다는 뜻입니다. 한꺼번에 여러 개를
  지우다 정답이 섞여 있어도 마찬가지입니다. 제안 단계에서도 지우려는 후보가 정답인지는 서버도 보지 않습니다.
- **난이도**: 후보 16개는 비슷한 종류 5개 카테고리에서 3~4개씩 뽑습니다(12개 카테고리에서 하나씩 뽑으면 힌트 하나에
  카테고리째 걸러집니다). 힌트는 5개를 다 알아도 후보가 7개 안팎으로 남게 짜고(힌트를 가장 잘 따라가도 정답을 맞힐
  확률이 16% 정도, 예전에는 29%), 후보 하나를 콕 집어 주는 판은 만들지 않습니다. 힌트의 절반 가까이는 "포근한 느낌 /
  서늘한 느낌", "소리로 기억남 / 모습으로 기억남"처럼 겉으로 안 드러나는 개념의 **어려운 축**입니다. 더 쉽게·어렵게 하려면
  `web/galpang/hint.js`의 `DIFFICULTY`(`target` 남는 후보 수, `hardShare` 어려운 축을 쓰는 비율)와
  `web/galpang/state.js`의 `CANDIDATE_SPREAD`(후보를 모으는 카테고리 수)를 고치고, `node test/galpang-hint-test.js`가
  기준을 지키는지 봅니다.
- 돈이나 칩은 걸지 않습니다.
- 서버 관리 로그(`[갈팡질팡]` 줄)에는 게임을 시작할 때 정답을 한 번 남깁니다(운영자가 판을 확인하는 용도). 화면으로는
  끝나기 전에 정답이 가지 않고, 그 밖의 로그 줄에는 후보를 번호로만 씁니다.
- 정답은 서버만 알고, 게임이 끝나기 전에는 브라우저에 보내지 않습니다. seed도 내보내지 않습니다
  (규칙 코드가 공개돼 있어 seed를 알면 정답을 계산할 수 있습니다).
- 모든 조작은 명령어 한 줄입니다(`remove 3 5`, `guess 5`, `next`, `list`, `history`, `help`, `quit`,
  `restart`, 한글 `제거 3`·`정답 5`·`다음`도 됩니다). 화면의 버튼과 "명령어로 입력하기" 입력칸이 같은 명령을 씁니다.
  여럿이 할 때 판을 바꾸는 명령은 제안이 되고, 찬반은 화면의 투표 창으로 합니다. 도움말·목록·기록은 그 사람에게만 답합니다.
- 터미널에서는 혼자 하는 같은 규칙으로 할 수 있습니다(동의 절차 없음).

```bash
npm run galpang                          # 새 게임
npm run galpang -- --seed 100            # 같은 seed면 후보·정답·힌트가 같습니다(재현용)
npm run galpang -- --seed 100 --debug    # 정답·힌트 계획·상태 전이를 보여 줍니다(개발용)
```

| 위치 | 하는 일 |
|---|---|
| `web/galpang/engine.js` | 규칙·상태(INIT → PLAYING → WON / LOST / QUIT). 출력과 입력 읽기는 하지 않습니다 |
| `web/galpang/hint.js` | 힌트 5개를 시작할 때 정해 두고 라운드마다 하나씩 공개합니다. 공개 전 품질 검사 |
| `web/galpang/parser.js` · `renderer.js` · `actions.js` · `session.js` | 명령어 해석 · 글자 출력 · 판을 바꾸는 명령의 실행(터미널과 사이트가 같이 씁니다) · 터미널의 대화 흐름(포기 확인 등) |
| `web/galpang/data/words.json` · `hints.json` | 단어 576개(12개 카테고리 × 48)와 그 특징 · 힌트 축 140개(난이도 1~5, 난이도마다 23~30개, 그중 어려운 축(`hard`) 48개) |
| `web/galpang-room.js` | 사이트용 방. 방 하나에 판 하나를 여럿이 같이 하고, 준비 → 시작, 과반수 동의 제안·투표, 구경, 끊겨도 같은 토큰이면 같은 자리로 돌아오는 재접속을 맡습니다 |

단어나 축을 추가·수정하면 `node test/galpang-hint-test.js`가 오타·모순·편중을 잡아 줍니다.

## Render 배포

1. Render에서 이 저장소를 Web Service로 연결합니다.
2. Build Command는 `npm ci --omit=dev`, Start Command는 `npm start`로 설정합니다.
3. Health Check Path는 `/healthz`로 설정합니다.
4. 지연 없는 운영이 필요하면 휴면하지 않는 유료 인스턴스를 선택합니다.

화면과 `/api/ws` WebSocket은 같은 Render 인스턴스에서 제공됩니다. 배포나 일시적인
네트워크 단절로 연결이 종료되면 화면이 자동으로 다시 연결합니다.

커스텀 도메인에서 Origin 검사가 실패하면 Render의 Environment Variables에
`LIAR_ALLOWED_ORIGINS=https://game.example.com` 형식으로 추가합니다. 여러 도메인은 쉼표로
구분합니다. 같은 호스트에서 제공된 화면은 자동 허용됩니다.

## 현재 제약

게임 상태는 Render 인스턴스 메모리에 있습니다. 배포나 인스턴스 재시작 시 진행 중인 방은
초기화됩니다. 재시작 후에도 상태를 유지해야 한다면 Redis 기반 저장 기능이 추가로 필요합니다.

- **게임 주소는 Render(`*.onrender.com`) 하나입니다.** 인스턴스는 1개로 둡니다. 여러 개로 늘리면
  같은 게임에 들어가도 인스턴스마다 방이 따로 생겨 서로 보이지 않습니다.
- **Vercel 배포는 게임 주소로 쓰지 않습니다.** 저장소의 `vercel.json`·`api/ws.js` 때문에 PR마다
  Vercel에도 배포되지만, Vercel은 접속마다 다른 함수 인스턴스로 연결될 수 있고 인스턴스마다 방이
  따로 생깁니다. 같은 주소로 들어가도 서로 다른 방에 들어갈 수 있으니 Vercel 주소는 공유하지 마세요.
